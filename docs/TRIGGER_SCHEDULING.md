# Trigger scheduling

Time schedules support daily, selected weekdays/weekly, monthly (clamped to month's last day), selected dates/once, anchored N-day intervals, multiple clock times and inclusive start/end dates. The next occurrence alone is scheduled. `device` follows the device timezone; explicit IANA zones remain fixed. Android API 29 provides java.time.

DST gaps move forward by the gap; ambiguous local times use the earlier offset. Clock and timezone receivers reconcile schedules. Exact AlarmManager access is checked on API 31+; revocation/security errors fall back to `setAndAllowWhileIdle`. WorkManager provides a durable deferrable fallback. Although alarm delivery can be exact, execution is delegated to workers and may be delayed. Neither periodic recovery nor geofencing is an exact timing guarantee.

Weekly windows start on WINDOWDAY at the first configured clock time and end one week later, end-exclusive. Stable window keys deduplicate executions across original delivery and permitted catch-up. Recovery evaluates the current window, so Friday delivery missed and recovered Sunday remains eligible. Non-window recovery uses the same occurrence identity as its original alarm. Grace defaults to one hour. `skip` does not start catch-up; `grace` permits recovery within grace; `window` permits current weekly-window catch-up. `ask` creates a durable yes/no interaction with a one-hour deadline before the original workflow: Yes proceeds, No stops. Missed events under `record` and `skip` are recorded in diagnostics. There is no separate durable missed-event table. Delivery verifies the saved definition version and occurrence identity, even when reconciliation has already scheduled the next occurrence.

Location monitoring uses Google Play Services enter/exit/dwell events, minimum radius 100 m, maximum 100 registered locations, two-minute dwell/responsiveness hints and no fabricated initial event. Registration status is set only after the API result. Missing precise/background permissions, disabled location or unavailable Play Services produce visible failure states. Occupancy starts UNKNOWN and expires after one hour. Cooldown and stable event keys suppress repeat starts. Location triggers apply DAYS, ZONE, START/END dates and optional ELIGIBLEFROM/ELIGIBLETO local clock times before starting a run. Both clock fields must be supplied together; blank means all day, equal times mean all day, and end is otherwise exclusive. In overnight windows, the after-midnight portion belongs to the starting day/date (Friday 22:00–02:00 includes Saturday 01:00). Occupancy updates even when an event is outside workflow eligibility.
